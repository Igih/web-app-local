# 代码 Agent 总提示词：图像资源管理增量改造 V2

你是一名熟悉 Docker Compose、Nginx、Node 前端、FastAPI、PostgreSQL 及大规模图像管理的资深全栈工程师。请基于我已经部署的**内网管理网站**进行增量改造，**原有菜单与业务不动，只新增一个「图像资源管理」一级菜单及其子页面**。

## 一、绝对约束

1. 原技术栈：Docker Compose + Nginx + Node/前端 + FastAPI/Python + PostgreSQL。优先复用现有代码架构、认证、授权、ORM、日志和迁移机制，不新建重复框架。
2. 数据存于宿主机持久化目录（Bind Mount），不是Docker镜像或容器普通可写层；FastAPI尽量只读原图，独立Worker处理扫描和写入。
3. 图片按SHA-256识别完全重复并按哈希分级目录存储；保留源机器、原路径、原文件名、原始类别和类型声明。
4. 本期不做训练数据集构建、FiftyOne、Agent集成、AI自动分类，也不解析目标框/分割/旋转框等标注内容。

## 二、必须满足的业务需求

- 六种花卉类别固定为：**牡丹、菊花、月季、郁金香、玫瑰、太阳花**。
- 图片类型采用两级分类：
  - 一级：**实拍(photo)**、**手绘(hand_drawn)**；
  - 二级：**可见光(visible)**、**红外(infrared)**。
- **检索界面始终展示四种组合：实拍·可见光、实拍·红外、手绘·可见光、手绘·红外**，即使某项当前统计为0也不得隐藏。
- 导入表单只有**图片路径和花卉类别必填**；标注路径、一级类型、二级类型、自定义标签可空。类型不填以“未指定”保存；一级未指定时二级也必须未指定；一级指定后二级可以未指定。
- 图片路径与标注路径均可选**服务器端授权目录中的文件或文件夹**；目录默认递归扫描。区分服务器路径导入与浏览器本地文件上传，当前优先实现前者。
- 每张图片最多5个自定义标签，标签库不限数量；支持标签 AND/OR 检索，并与类别、两级类型进行组合筛选。
- 一张图片可以无标注；标注存在时根据文件名、相对路径关联并原样存储；歧义匹配须报告而不是猜测。
- 对 SHA-256 重复的文件仅保留一份原图，但保留多条来源。类别/两级类型/标签发生冲突时记录待审，不静默覆盖旧值。
- 统计必须涵盖六类×四种完整类型组合、未指定类型、源文件数量、唯一图片数量、重复数、损坏数、冲突数。
- 红外原始图（如16-bit TIFF）不得被缩略图流程破坏；不根据通道数自动认定红外或可见光。
- 有扫描预览、用户确认、后台任务、进度、错误记录、幂等、失败重试；必须进行路径白名单校验、权限控制、审计和备份设计。

## 三、模块划分

M1. 环境适配、Bind Mount与独立Worker。  
M2. PostgreSQL `asset` Schema、迁移、约束与索引。  
M3. 六类、两级图片类型、自定义标签及5标签约束。  
M4. 数据导入表单、文件/目录路径校验、扫描预览。  
M5. 导入引擎、SHA-256去重、原图和缩略图存储、任务恢复。  
M6. 标注文件原样存储与图片关联。  
M7. 图片列表/详情/批量维护、四组合类型筛选、标签AND/OR。  
M8. 六类及实拍/手绘×可见光/红外统计、任务和异常报告。  
M9. 集成测试、旧业务回归、性能与备份恢复验证。

## 四、执行顺序与交付约束

**现在只执行“第0步：工程审查”，禁止修改代码或数据库。**

请检查：
1. 现有 Docker Compose 的服务、构建入口、卷、网络与权限；
2. 前端框架及菜单/路由组织方式；
3. FastAPI 的入口、Router、Service、认证与授权；
4. PostgreSQL 的 ORM、Schema、迁移及现有数据表；
5. 已有图片/文件管理能力及可复用代码；
6. 新模块对旧业务可能造成的兼容风险。

然后输出：
- 真实项目结构及依赖分析；
- 新菜单、新页面、新API和数据库表的落点；
- PostgreSQL表结构建议与两级类型字段的合法取值及未指定规则；
- Docker Compose最小增量配置与文件目录映射；
- 逐模块文件修改清单、任务顺序和验收标准；
- 风险、测试清单和回滚计划。

**得到我明确指令后才开始对应模块。** 每次仅执行指定模块，先列出将修改的文件和方案，再实现；运行测试并如实报告测试命令、结果、变更、未完成项及回滚步骤。不可在缺乏独立验证时宣告成功。
